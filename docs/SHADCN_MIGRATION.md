# ТЗ для Codex: миграция Aerion на shadcn-svelte

## 1. Цель

Провести комплексную миграцию frontend почтового клиента Aerion на современную дизайн-систему **shadcn-svelte**.

Исходный проект:
https://github.com/hkdb/aerion

Целевая библиотека:
https://github.com/huntabyte/shadcn-svelte

Документация:
https://shadcn-svelte.com/docs

Основные задачи:

- Перейти на актуальную совместимую версию shadcn-svelte.
- Обновить Tailwind CSS с v3 на v4.
- Использовать актуальные совместимые версии Bits UI.
- Стандартизировать компоненты пользовательского интерфейса.
- Сократить систему тем до Dracula и Nord Dark.
- Удалить устаревшие темы, стили, компоненты и зависимости.
- Сохранить существующую функциональность приложения.
- Упростить дальнейшее развитие и поддержку frontend.

Это задача на **непосредственную реализацию**, а не только анализ или составление рекомендаций.

Работай последовательно, самостоятельно принимай обоснованные технические решения и доведи миграцию до работоспособного состояния.

## 2. Ограничения

### Обязательно сохранить

- Go backend и бизнес-логику.
- Wails v2 и существующий механизм Go ↔ Svelte.
- IMAP/SMTP, OAuth2 и управление аккаунтами.
- Синхронизацию и локальное хранение почты.
- Списки писем и виртуализацию TanStack.
- Создание, редактирование, отправку писем.
- TipTap и все функции редактора.
- Работу с вложениями.
- Настройки аккаунтов и приложения.
- Переводы и локализацию.
- Горячие клавиши.
- Контекстные меню, диалоги и уведомления.
- Работу на поддерживаемых ОС.

### Запрещено

- Переписывать приложение на SvelteKit.
- Мигрировать Wails v2 на Wails v3 в рамках этой задачи.
- Заменять или переписывать Go backend без необходимости.
- Удалять функциональность ради упрощения UI.
- Добавлять вторую конкурирующую дизайн-систему.
- Массово переписывать работающие компоненты без необходимости.
- Оставлять две независимые системы стилизации.
- Подавлять ошибки TypeScript через `any`, `@ts-ignore` или отключение проверок.
- Удалять тесты вместо их исправления.

Изменения должны оставаться сфокусированными на frontend, его интеграции и настройках тем.

## 4. Миграция Tailwind CSS 3 → 4

Выполни полноценный переход на Tailwind CSS 4 в соответствии с официальной документацией.

Требования:

- Подключить актуальную совместимую версию Tailwind CSS.
- Использовать `@tailwindcss/vite` при совместимости с конфигурацией проекта.
- Перевести конфигурацию темы на CSS-first подход с `@theme` / `@theme inline`.
- Удалить устаревшую конфигурацию Tailwind 3, если она больше не используется.
- Обновить deprecated utilities.
- Проверить все кастомные анимации.
- Сохранить поддержку расширений, включая пути вне `frontend/`.
- Проверить CSS, генерируемый production build.
- Устранить конфликты со стилями Wails WebView.

Проверь поддержку используемых CSS-возможностей в реальных WebView поддерживаемых платформ.

Не используй динамически формируемые имена Tailwind-классов, которые не обнаруживаются компилятором.

Обязательно проверь классы с opacity, произвольные значения, кастомные цвета, обработку dark mode, ring, border, focus, hover и disabled.

## 5. Интеграция shadcn-svelte

Настрой shadcn-svelte для **обычного Svelte 5 + Vite проекта без SvelteKit**.

Используй официальные инструкции:

https://shadcn-svelte.com/docs/installation/vite

Требования:

- Добавить корректный `components.json`.
- Проверить alias `$lib` и TypeScript paths.
- Обновить Bits UI при необходимости.
- Настроить общий helper `cn()`.
- Использовать единый подход к вариантам компонентов через Tailwind Variants.
- Организовать компоненты внутри `frontend/src/lib/components/ui/`.
- Не допускать дублирования одинаковых компонентов.
- Сохранить совместимость с существующими Svelte 5 runes и snippets.

Перед применением shadcn CLI проверь возможные конфликты с существующими файлами.

Не запускай автоматическую перезапись существующих компонентов без предварительного анализа.

При необходимости используй временную директорию для сравнения генерируемых компонентов с существующими.

## 7. Темы оформления

Полностью упрости систему оформления.

### Поддерживаемые темы

| ID | Название | Режим |
|---|---|---|
| `dracula` | Dracula | Dark |
| `nord-dark` | Nord | Dark |

**Тема по умолчанию — Nord.**

Под названием Nord в интерфейсе подразумевается существующая тёмная палитра `nord-dark`.

Других пользовательских тем и режимов Light/System быть не должно.

### Dracula

Используй оригинальную цветовую палитру Dracula.

Основные цвета:

- Background: `#282A36`
- Current Line: `#44475A`
- Foreground: `#F8F8F2`
- Comment: `#6272A4`
- Purple: `#BD93F9`
- Cyan: `#8BE9FD`
- Green: `#50FA7B`
- Red: `#FF5555`
- Yellow: `#F1FA8C`

### Nord

Используй оригинальную тёмную цветовую палитру Nord.

Основные цвета:

- nord0: `#2E3440`
- nord1: `#3B4252`
- nord2: `#434C5E`

Дополнительно сохрани необходимые Aerion-specific токены, например для аватаров, непрочитанных писем, выделения сообщений и иных состояний.

Выбери единый формат хранения цветов, совместимый с Tailwind 4 и текущим shadcn-svelte.

Не смешивай несовместимые способы использования CSS-переменных.

Убедись, что обе темы одинаково поддерживают компоненты, всплывающие меню, диалоги, состояние focus и редактор.

### Удаление старых тем

Удалить из пользовательского выбора и итоговой сборки все темы, кроме Dracula и Nord Dark.

Убрать неиспользуемые CSS-файлы, импорты, константы и настройки.

Не удалять вспомогательные общие стили, если они необходимы оставшимся темам.

### Совместимость настроек

Обнови:

```text
internal/settings/store.go
frontend/src/lib/stores/settings.svelte.ts
frontend/src/lib/components/settings/GeneralTab.svelte
frontend/src/lib/stores/theme.svelte.ts
```

Последний путь проверь по фактическому состоянию проекта.

Правила:

- Существующее значение `dracula` сохраняется.
- Существующее значение `nord-dark` сохраняется.
- `nord-light` и все прочие ранее поддерживаемые значения преобразуются в `nord-dark`.
- Новые установки используют `nord-dark`.
- Неизвестное или повреждённое значение безопасно преобразуется в `nord-dark`.
- Сохранённый выбор темы сохраняется после перезапуска приложения.
- В Go backend и frontend действуют одинаковые правила нормализации.
- Удаление старых тем не должно препятствовать загрузке существующих настроек.

Не выполнять разрушительную миграцию базы данных ради смены темы.

### Управление темами

В настройках оставить ровно два варианта:

```text
Appearance
  Theme
    Nord
    Dracula
```

Переключение должно работать без перезапуска.

Сохранить действующие настройки отображения HTML-письма и тела редактора, включая возможность использовать светлый фон для содержимого письма.

Тёмная тема интерфейса не означает, что HTML-письма необходимо принудительно перекрашивать.

## 13. Git и отчётность

Работай в текущем репозитории.

В репозитории используются только две ветки: `main` и `dev`. Все изменения миграции выполняй в `dev`.

Не изменяй `main` напрямую и не создавай дополнительные ветки задач или релизов. Перенос проверенных изменений из `dev` в `main` выполняется только по запросу пользователя; общий процесс описан в `CONTRIBUTING.md`.

Не применяй `git reset --hard`, не выполняй принудительную отправку изменений и не удаляй пользовательские незакоммиченные правки.

Выполняй небольшие логические коммиты по мере завершения этапов.

Рекомендуемые названия:

```text
refactor(ui): migrate frontend to tailwind v4

```

Названия адаптируй к фактически выполненным изменениям.
